Follows the ImportFromVAM.html pattern: a semantic-search keyword input feeding a semantic-table over the 'ephedra' federation repository. SOURCE KNOB. semantic-search-query-keyword owns exactly one query, so a source selector has to be a choice between panels rather than a control inside one. Hence nested rs-tabs: Wikidata + GND UNION of the two general-purpose sources in one query Wikidata wbsearchentities — broad, English, concepts and agents GND lobid.org — German labels; search "Vergoldung", not "gilding" VIAF AutoSuggest — personal/corporate NAMES only, useless for concepts AAT Getty — concepts with real definitions (inline SERVICE, see below) The single-source tabs are also the fallback when a service is down: UNION is all-or-nothing, so one failing branch returns zero rows for the combined tab, while the other tabs keep working. VIAF is deliberately NOT in the union, for two reasons: it returns personal/corporate names only, which is pure noise when the record being aligned is an E55 concept; and every union search would spend one unit of its shared ~1000/day quota even when nobody wanted names. It stays available on demand in its own tab. resultsPerPage is 30, not 10, because UNION branches come back contiguously grouped by source — at 10 the first page was entirely Wikidata and the GND rows sat on page 2+, which reads as "GND returns nothing". Deliberately NO ORDER BY: sorting would group the sources but destroy each service's own relevance ranking within the group. Every row's URI comes from its own authority, so there is no third-party crosswalk claim to verify. Mint = copy the URI and paste it into a match field below; the field you paste into IS the alignment property, so no property chooser is needed here. Two things to know before editing the queries: 1. ?__token__ is substituted at every occurrence (SparqlClient.setBindings), so one box feeds all three branches of the UNION. 2. Sparse fields are safe to bind. A jsonPath that resolves to null omits just that binding and leaves the row in place with the variable unbound — verified against wikidata-entity: 31 rows both with and without the ?description binding, 28 of which carried a description. This is why ?description can be projected freely. (What is NOT possible is OPTIONAL inside a RESTSail SERVICE block.) Descriptions per source: Wikidata has a real one; GND has no `definition` field, so the query COALESCEs its three substitutes (biographical note / subject category / profession); VIAF AutoSuggest carries none, so the cell stays empty by design. The "Match / kind" column is deliberately source-specific — Wikidata's match.type (did this hit the label or an alias?), GND's entity type, VIAF's name type. It answers "why is this row here?", which is the question a noisy result list actually raises. Wikidata's QID is NOT shown: it is already in the row's href, and it disambiguates nothing. No image column, on purpose. GND's depiction covers 6/98 records, VIAF has no image field at all, AAT has none by nature, and Wikidata's P18 needs a second call per row — while preferredThumbnails in config/ui.prop already fetches P18 for any minted Wikidata owl:sameAs, which is where a picture actually helps. See §7 of the doc. VIAF enforces ~1000 requests/day per deployment IP, shared by all users, and each search costs one. Fine for hand-driven alignment; never put a batch process behind it. See docs/features/external-authority-federation.md --]]
